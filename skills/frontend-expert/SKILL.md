# Frontend expert

Build frontend work as a real product surface: usable first, visually intentional second, animated only where motion helps the user understand state or flow.

## Core judgment

- Start from the user's job, audience, data, device context, and existing product style.
- Prefer a clear product interface over a landing-page composition unless the user asked for marketing.
- Keep the first screen useful. Do not make a decorative hero when the app needs a tool, dashboard, editor, form, or workflow.
- Use the existing framework, design system, tokens, component library, and routing patterns unless the user asks for a new direction.
- Spend visual boldness in one or two memorable places. Keep the rest quiet enough to support repeated use.
- Preserve function. A beautiful UI that breaks existing behavior is a failed change.
- Avoid generic AI defaults: purple-blue gradients, floating blobs, identical cards, fake stats, placeholder copy, overlarge headings in narrow columns, and motion on everything.

## Required design pass

Before writing frontend code, decide:

- Product type: dashboard, SaaS tool, editor, storefront, portfolio, game, data app, marketing page, docs, or internal ops.
- Primary workflow: the one thing the user must be able to do quickly.
- Information hierarchy: what must be seen first, scanned second, and hidden until needed.
- Visual direction: 4-6 colors, type roles, spacing density, border radius, icon style, and one signature element tied to the subject.
- States: loading, empty, error, disabled, hover, focus, active, selected, expanded, success, and responsive layout.
- Verification: which browser viewport and interaction checks are needed before done.
